## Task 1: Iterative Resolver

### Public interface and output

The required interface remains:

```python
Resolver().resolve(name) -> (address, path)
```

`address` is one IPv4 `A` record represented as a string. `path` is a list of every
server IP actually queried in chronological order, including failed server attempts and
the nested queries required to resolve a nameserver that arrived without glue. The
first path element is always one of `ROOT_SERVERS`.

The existing command-line behavior is preserved:

```bash
python3 task1_resolve.py www.korea.ac.kr
python3 task1_resolve.py --verify
```

### Transport and parsing

The default transport shells out to `dig`; it never invokes `dig +trace`. Every query in
the iterative walk names the target server explicitly and disables recursion:

```text
dig @SERVER NAME A +norecurse +time=2 +tries=1
```

The implementation requests enough output to retain the DNS status, flags, answer,
authority, and additional sections. A small internal reply representation records:

- status and whether the `aa` flag is present;
- answer-section `A` and `CNAME` records;
- authority-section `NS` records;
- additional-section `A` records.

Names are normalized to lowercase without a trailing dot. Resource-record lines are
parsed by field position rather than by alignment whitespace. Timeout, nonzero process
status, malformed output, or an unusable response becomes a failed candidate, not a
recursive fallback.

### Resolution algorithm

1. Begin with the three `ROOT_SERVERS` as ordered candidates.
2. Ask candidates in order and append each attempted address to `path`.
3. Accept an `A` only from the answer section of an authoritative response. Glue is
   never returned as the requested answer.
4. On a referral, read the authority-section NS names. Use additional-section IPv4 glue
   only when its owner matches one of those NS names.
5. For an NS with no usable glue, perform a new iterative walk from the roots for the NS
   hostname. The nested walk shares the chronological path and depth/loop guards.
6. If one delegated server times out, is lame, or cannot be reached, try the next NS or
   its resolved address before failing the delegation.
7. On `CNAME`, discard the current delegation state and restart from the roots for the
   normalized target. Even if the response also contains a convenient terminal `A`, the
   fresh walk makes the required CNAME behavior explicit and auditable.
8. Detect active-name/CNAME cycles and cap nested resolution at 32 transitions. A cycle,
   authoritative negative answer, or exhaustion of every candidate raises a descriptive
   resolution exception; it never hangs.

An optional injected transport is allowed for tests, while `Resolver()` without
arguments retains the required student interface.

### Unit coverage

- CNAME restart at a root;

- rejection of an additional-section `A` as the final answer;
- the invariant that `path[0]` belongs to `ROOT_SERVERS`.

## Task 2: Capture and DNS Steering

Task 2 has a strict provenance boundary. Code may collect, preserve, validate, compare,
and render data, but it must not invent a capture, a second vantage point, packet
numbers, ownership judgments, or a conclusion. `report()` refuses to publish a complete
report until the user-authored evidence passes validation.

### CLI decisions

The documented modes remain and gain explicit measurement context:

```bash
python3 task2_steering.py --collect --network campus-wifi
python3 task2_steering.py --collect --network phone-tethering
python3 task2_steering.py --report
```

`--network LABEL` is optional only for backward compatibility; omitted labels are stored
as `network-1`. A final report rejects generic labels because the assignment requires
both networks to be named. Reusing an existing label is rejected to protect evidence;
the student may deliberately replace it with:

```bash
python3 task2_steering.py --collect --network campus-wifi --replace
```

`--replace` is valid only with `--collect`. `--report` reads
`out/task2_evidence.json` by default. An optional `--evidence PATH` accepts the same
schema from another local path without changing the required output locations.

### DNS collection

For each of the exact 12 entries in `SITES`, collection performs the following on the
current network:

1. Follow one system-resolver CNAME at a time, storing the original name and every
   normalized target until no CNAME remains.
2. Cap the chain at 16 edges and reject loops.
3. Find both the original site's and final target's authoritative zones by querying
   successively shorter suffixes for `SOA`; this avoids treating `co.uk` or `ac.kr` as
   an organizational zone merely because they are the last two labels and supplies both
   inputs to the classification rule.
4. Ask every entry in `RESOLVERS` for the original site's `A` records.
5. Keep only valid IPv4 strings, sorted and deduplicated as an address set.
6. Preserve lookup errors separately. An empty address list is not silently treated as
   a successful no-address answer.

The chain length shown in the report is the number of CNAME edges, `len(chain) - 1`, not
the number of names in the stored list.

### `out/chains.json` schema

The top level contains exactly the 12 site names so the supplied harness's `len(data)`
continues to mean site count. A second collection merges another measurement under each
site instead of replacing the first:

The real `classifications` object must contain all 12 sites, not only the abbreviated

capture object additionally requires `whose_machine_and_evidence` and the exact

as the student's traffic.

### Classification rule and report calculation

The automated rule is intentionally simple and independently testable:

> Rule verdict: a site is third-party-served when the final authoritative DNS zone
> differs from the original site's authoritative DNS zone.

The report's `third party?` column is the student's reviewed ownership judgment from
`task2_evidence.json`; `rule verdict` is the automated zone comparison. CDN-hosted and
third-party are separate booleans because a first-party CDN, such as Netflix's, still
belongs in the steering denominator.

For each student-classified CDN-hosted site, the reporter collects every nonempty
address set across all `(network, resolver)` pairs. The site counts as different once if
at least two of those sets differ. It then emits the required sentence:

```text
X of N CDN-hosted sites answered differently to a different resolver or network.
```

The reporter does not infer geographic proximity from different addresses. It includes
the student's `steering_conclusion`, which must acknowledge relevant limits such as
temporal load balancing, resolver caches, or anycast. At least one site's reviewed
judgment must disagree with the rule verdict, and its evidence reason must explain why;
otherwise report generation fails rather than manufacturing a required mistake.

The Markdown report includes:

- `site | chain length | final zone | third party? | rule verdict`;
- named results for both networks, with per-network chain/zone values when they differ;
- the steering number and student conclusion;
- the mismatched classification and explanation;
- the matched query/response transaction ID;
- delegation and answer response packet numbers;
- DNS-message and frame byte counts plus the student's size explanation;
- official-trace attribution and provenance explanation when path B is used.

## Task 3: TTL-Correct Cache

### Public interface

`YourCache` preserves the complete interface required by `task3.md`:

```python
YourCache(upstream)
lookup(name, now) -> address
stats() -> {"entries": int}
```

Entries are held in a dictionary:

```text
name -> (address, expires_at)
```

A cached answer is returned only while `now < expires_at`. At or after expiry, the
entry is removed and `upstream(name)` is called. A new positive-TTL answer stores
`expires_at = now + ttl`. A zero or negative TTL answer is returned to the current
caller but is not reusable. `stats()` retains the baseline's exact key and value shape.
The supplied simulated `now` is the sole clock; the implementation does not call wall
time.

### Baseline diagnosis and optimum

The baseline discards each authoritative TTL and substitutes 60 seconds. That single
cause creates two distinct required observations:

- correctness defect: 20- and 30-second records are served after expiry;
- performance defect: records with TTL greater than 60 seconds are fetched too early.

Its list representation also imposes a linear scan, but that is separate from the two
TTL defects requested by the exercise.

For seed 246 and the supplied 1,000-query workload, the optimal correct result is:

```text
upstream 275
hit rate 72.5%
stale 0
sim time 5.5s
```

The upstream-call floor by fixture entry is:

| Name | Calls |
|---|---:|
| `www.microsoft.com` | 118 |
| `www.cnn.com` | 76 |
| `www.netflix.com` | 37 |
| `www.spotify.com` | 23 |
| `www.github.com` | 11 |
| `www.wikipedia.org` | 6 |
| `www.korea.ac.kr` | 1 |
| `www.stanford.edu` | 1 |
| `dns.google` | 1 |
| `a.root-servers.net` | 1 |
| **Total** | **275** |

The first request for a name requires an upstream answer. After that fetched answer's
TTL interval, the first subsequent request requires another upstream answer. Waiting
until that request is optimal: prefetching costs a call no later and cannot extend
freshness farther than fetching on demand, while reusing the old answer would be stale.
Therefore no correct on-demand cache can go below 275 on this fixed workload.

`www.microsoft.com` is the baseline's worst fixture entry because it combines the
shortest TTL, 20 seconds, with the highest query frequency. Keeping it for 60 seconds
produces 189 of the baseline's 266 stale answers; CNN produces the other 77.
