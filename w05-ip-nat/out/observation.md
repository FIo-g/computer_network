# 5주차 관찰 기록

## Task 1 · 서브넷과 최장 접두사 일치

`python3 task1_forward.py --verify`는 `10/10 ok`로 끝났다. `ipaddress`도 `socket`도 쓰지 않고 시프트와 마스크만 썼다(R6).

/31과 /32에서 돌려주는 값(실제 출력):

```
10.0.0.4/30 ('10.0.0.5', '10.0.0.6', '10.0.0.7')
10.0.0.0/31 ('10.0.0.0', '10.0.0.1', None)
10.0.0.5/32 ('10.0.0.5', '10.0.0.5', None)
```

/30까지는 교과서 규칙대로 네트워크 + 1부터 브로드캐스트 - 1까지를 쓰고 브로드캐스트를 따로 돌려준다. /30이면 쓸 수 있는 주소가 2개다. /31은 RFC 3021을 따랐다. 두 주소를 모두 호스트로 쓰고 브로드캐스트는 없다. 점대점 링크에는 상대가 하나뿐이라 네트워크 주소와 브로드캐스트를 비워 둘 이유가 없고, 교과서 규칙을 그대로 적용하면 쓸 수 있는 주소가 0개가 되어 링크를 쓸 수 없다. /32는 서브넷이 아니라 호스트 하나(호스트 경로)라서 (주소, 주소, None)을 돌려준다. 내 Mac의 utun4가 바로 이 모양이다(`inet 100.79.x.x --> 100.79.x.x netmask 0xffffffff`, 주소 뒤 두 자리는 가림). 브로드캐스트 자리에 주소처럼 생긴 값을 넣지 않고 `None`을 둔 건, 호출하는 쪽이 그 값을 진짜 주소로 믿고 보낼 수 있어서다.

10.20.30.70은 네 항목에 맞았고, 기본 경로까지 치면 다섯이다(실제 출력):

```
0.0.0.0/0        /0  default-gw    match
10.0.0.0/8       /8  campus        match
10.20.0.0/16     /16 eng-building  match
10.20.30.0/24    /24 lab-floor     match
10.20.30.64/26   /26 lab-rack-2    match
192.168.1.0/24   /24 home          -
winner: lab-rack-2
```

/26이 맞는지는 손으로 확인했다. 마지막 옥텟 70은 01000110이고 /26 마스크의 마지막 옥텟은 11000000이다. AND하면 01000000 = 64라서 10.20.30.64다. 승자를 고른 규칙은 가장 긴 접두사다. 내 표는 길이별 dict이고, 들어 있는 길이를 긴 것부터(26, 24, 16, 8, 0) 물어서 처음 맞는 곳에서 멈춘다. /0은 늘 마지막에 물으니 다른 어떤 일치에도 진다(R5).

같은 길이의 같은 접두사가 두 번 들어오면(실제 출력):

```
same hop twice: ok -> a
ValueError: 10.0.0.0/8 is already in the table -> 'a'; refusing a second next hop 'b'
```

다음 홉까지 같으면 아무 일도 하지 않고, 다르면 `ValueError`로 거부한다. 길이가 같으면 어느 쪽이 더 구체적인지 가릴 수 없어서 최장 일치가 답을 못 정한다. 그건 표가 잘못된 것이다. 조용히 하나를 고르면 넣은 순서가 전달 결과를 바꾸게 된다. Task 3의 `LinearTable`은 `plen > best`(엄격한 부등호)라서 먼저 넣은 쪽이 조용히 이기는데, `YourTable`은 R3(모든 답이 같아야 함) 때문에 그 동작을 그대로 따랐다. 길이가 같아도 10.20.30.0/24와 192.168.1.0/24처럼 네트워크가 다르면 겹치지 않으니 문제없다.

## Task 2 · 나는 인터넷 어디에 있나

자세한 분석은 `out/report.md`에 있다.

NAT 층수는 네트워크마다 달랐다. KU Wi-Fi에서는 en0이 172.16.19.123(RFC 1918)이고 바깥에서는 163.152.233.19로 보이니 NAT가 최소 한 겹이다. traceroute에서 공인 주소는 hop 3부터 나오고 그 앞에 사설 hop이 두 개 있었다. 그중 어디서 몇 번 변환하는지는 traceroute로 가를 수 없었다. 핫스팟은 더 재밌었다. IPv4 주소를 아예 받지 않았다. iPhone이 DHCP Offer에 옵션 108(RFC 8925, IPv6만 써도 됨)을 넣었고, macOS는 192.0.0.2를 스스로 붙인 다음 IPv4 패킷을 Mac 안에서 IPv6로 바꿔(CLAT) 내보냈다. 통신사의 NAT64가 그걸 다시 IPv4로 바꿔서 211.235.91.7로 내보낸다. 번역은 두 번이지만 상태 있는 NAT는 NAT64 한 번이다. IPv6에는 NAT가 없어서 Cloudflare가 내 임시 IPv6 주소를 그대로 봤다.

utun4의 100.79.x.x는 CGN 대역(100.64.0.0/10)에 있어서 처음엔 통신사 NAT의 증거처럼 보였다. 하지만 DNS 설정의 `tailXXXXXX.ts.net`(가림)을 보면 Tailscale 주소였다. 기본 경로가 en0이니 NAT 층수와는 관계없다. 주소 대역만 보고 판단했으면 틀렸을 것이다.

두 네트워크 사이에서는 거의 모든 값이 바뀌었다. 공인 주소는 가장 바깥 NAT를 누가 운영하느냐(학교 회선 대 SK Telecom)에 따라, 사설 주소는 누가 나눠 주느냐(학교 DHCP 대 아무도 안 줌)에 따라 달라졌다. 서브넷도 /24에서 /32로 바뀌었고 게이트웨이도 172.16.19.1에서 192.0.0.1로 바뀌었다. MAC 주소마저 바뀌었다. macOS가 네트워크마다 다른 개인 Wi-Fi 주소를 쓰기 때문이다(2e:32:...와 66:f3:..., 둘 다 로컬 관리 비트가 1). 바뀌지 않은 건 인터페이스 이름 en0과 utun4의 Tailscale 주소 정도다.

KU Wi-Fi의 Discover는 출발 주소가 0.0.0.0이었다(frame 5). 아직 주소를 받기 전이라 쓸 주소가 없으니 다른 값일 수가 없다. 출발 주소가 없고 서버 주소도 모르니 목적지는 255.255.255.255일 수밖에 없다. 그래서 서버는 IP가 아니라 chaddr(2e:32:1f:50:ed:d9)와 xid로 클라이언트를 구분한다. 다시 연결하는 것만으로는 부족했다. macOS는 기억해 둔 임대 정보(`/var/db/dhcpclient/leases/en0.plist`)가 있으면 Request와 Ack만 주고받으므로, 그 파일을 지운 뒤 연결해서 Discover부터 잡았다.

## Task 3 · 최장 접두사 일치를 빠르게

`out/bench.txt` 결과는 strong이다.

| | build | lookup | lookups/s |
|---|---:|---:|---:|
| baseline | 0.00s | 5.367s | 3,726 |
| yours | 0.01s | 0.002s | 9,032,404 |

20,000개 답이 모두 선형 표와 같았고(`every answer matches`), 조회 속도는 2424.0배다. 벤치 밖에서도 정확한지 보려고 무작위 표 400개(시드 0~399)로 차분 시험을 했다. 접두사 길이 0~32, 무작위 추가 순서, 같은 접두사 중복 추가, 호스트 비트가 켜진 항목, 다음 홉 `None`, 추가 도중의 조회, 접두사 경계 ±1 주소를 섞었고 결과는 `differential: 165586 lookups, 0 mismatches`였다(`python3 out/differential_test.py`로 다시 돌릴 수 있다). `add()`에 넣는 길이 -1과 33, 네트워크 값 -1과 2^32는 `ValueError`로 거부한다. `lookup()`은 벤치 속도를 위해 입력을 검사하지 않으므로, 범위 밖 주소를 넣으면 엉뚱한 답이나 IndexError가 난다.

구조는 16, 8, 8비트 단계로 접두사를 펼치는 방식이다(DIR-24-8 계열). `_l16`은 65,536칸짜리 리스트로, 칸 번호가 주소 >> 16이다. /0~/16 접두사를 /16 칸 단위로 펼쳐 넣는다. `_d24`는 키가 주소 >> 8인 dict로, /17~/24를 /24 단위로 펼친다. /20 하나는 16개 키, /22 하나는 4개 키가 된다. 여기서 키를 찾으면 그 답은 /17 이상이라 `_l16`의 어떤 답보다 길다. `_deep`은 /25~/32가 있는 /24 블록마다 256칸 리스트를 두는데, 이 벤치에는 그런 접두사가 없어서 비어 있다(`_deep 0 blocks`). 칸마다 그 칸을 차지한 접두사 길이도 같이 저장하고 더 긴 접두사만 덮어쓰게 해서, 서로 다른 접두사끼리는 추가 순서가 결과를 바꾸지 않는다. 같은 접두사가 두 번 들어오면 Task 1 부분에 쓴 것처럼 먼저 넣은 쪽이 남는다.

메모리는 `out/lpm-compare.txt`(tracemalloc)에서 YourTable 2.61 MB, LinearTable 0.36 MB였다. `_l16` 65,536칸 × 2(다음 홉과 길이)와 `_d24` 13,553키 × 2가 대부분이다. 속도의 대가는 메모리와 추가 시간이다. /0 하나가 65,536칸을, /17 하나가 128키를 차지한다.

R5, 조회 시간이 무엇에 비례하는가. 표 크기 N이 아니라 단계 수다. 최대 세 번(`_deep` 확인, `_d24` dict 한 번, `_l16` 리스트 한 번)이고, 이 벤치에서는 평균 1.30번, 최대 2번이었다. `out/lpm-compare.txt` 2절에서 N을 1,000에서 100,000으로 늘렸을 때 YourTable은 108 ns에서 127 ns로, 1.18배 늘었을 뿐이다. LinearTable은 N이 1,000에서 20,000이 되는 동안 53.3 µs에서 1101.2 µs로 N에 비례해 늘었다. 단계 수가 N과 무관하다는 설명과 맞는다.

하드웨어가 비트 단위로 걷는 이유도 같은 파일 1절로 확인했다. 같은 표에 같은 20,000개 질문을 던졌다(생성: `python3 out/lpm_compare.py . > out/lpm-compare.txt`).

| 구조 | ns/lookup | 평균 단계 (최대) | 메모리 |
|---|---:|---|---:|
| 1비트 트라이 | 1294 | 21.36 (25) | 6.34 MB |
| 길이별 dict | 190 | 2.61 (7) | 0.22 MB |
| YourTable | 107 | 1.30 (2) | 2.61 MB |

Python에서는 한 단계를 진행할 때마다 인터프리터가 바이트코드를 여러 개 실행한다. 21단계짜리 트라이가 C로 구현된 dict 조회 2.6번을 이길 수가 없다. 여기서 비용은 메모리 접근 횟수가 아니라 Python 연산 횟수로 매겨진다. 하드웨어에서는 사정이 반대다. 해시는 길이마다 표를 하나씩(최대 33개) 물어야 하고 충돌과 재해시가 있어서 최악의 시간이 정해지지 않는다. 라인 속도로 전달하려면 평균이 아니라 최악의 경우가 보장돼야 한다. 트라이는 단계마다 정해진 메모리 읽기 한 번이라, 단계를 파이프라인으로 나누면 깊이와 상관없이 클록마다 패킷 하나를 처리한다. 지연은 단계 수만큼 생기지만 처리량은 일정하다. 단계 수는 멀티비트 트라이(스트라이드 8, 16)로 줄이는데, YourTable의 16, 8, 8도 같은 생각이다. 갱신이 국소적이라는 점도 있다. 접두사 하나가 바꾸는 노드가 정해져 있다.
